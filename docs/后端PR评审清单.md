## 一、接口契约一致性（必查）

这是后端 PR 的**第一优先级**。接口一旦偏离契约，Android 侧就会白做。

- [ ] 新接口路径与《接口契约》一致
- [ ] 请求/响应字段名、类型与契约一致
- [ ] 新增错误码已在契约第三章登记，且编号在本人负责区间内
- [ ] 响应体使用 `ApiResponse` 统一结构，没有直接 `return {...}`
- [ ] 分页接口使用 `PageData` 统一结构
- [ ] 时间字段为 ISO 8601 带时区
- [ ] 金额字段用字符串传输（不是 float）

> **若接口必须偏离契约**：先在契约文档更新并通知成员 3/4/5，再合并代码。**禁止先改代码后补文档。**

---

## 二、公共规范符合性

- [ ] 业务逻辑写在 `services/`，路由层只做参数接收与响应包装
- [ ] 抛 `BusinessException`，没有直接 `raise HTTPException` 绕过统一响应体
- [ ] 数据库操作通过 SQLAlchemy，没有拼接 SQL 字符串
- [ ] 第三方调用放在 `integrations/` 模块
- [ ] 第三方调用配置了超时（`httpx` 的 `timeout` 参数）
- [ ] 第三方失败有降级处理，**不会直接返回 500**

---

## 三、数据库规范符合性

- [ ] 模型改动已生成 Alembic 迁移脚本
- [ ] **没有手工改数据库结构**
- [ ] 新表包含 `created_at` / `updated_at`
- [ ] 需同步的表包含 `client_id` / `version` / `deleted_at`
- [ ] 金额字段用 `NUMERIC`，不是 `Float`
- [ ] 外键字段建了索引
- [ ] 敏感字段（密码、Token）存的是哈希
- [ ] 唯一约束已按《表关系与ER图》第四章落实

---

## 四、事务与并发

- [ ] 多表写入放在同一事务内
- [ ] 涉及余额、积分的操作有防重复机制
- [ ] 更新接口使用 `version` 做乐观锁
- [ ] 并发场景有数据库级约束兜底（不只是应用层判断）

---

## 五、安全

- [ ] 没有硬编码密钥、密码、API Key
- [ ] 敏感配置从环境变量读取
- [ ] 受保护接口加了 `CurrentUser` 依赖
- [ ] 管理接口加了 `CurrentAdmin` 依赖
- [ ] 查询用户数据时带了 `user_id` 过滤（**防越权**）
- [ ] `.env` 未被提交

- [ ] 新增接口补了 Swagger `summary` / `description`
- [ ] 日志记录了关键业务节点，且未打印敏感信息
