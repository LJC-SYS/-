### 1.2 统一响应体（所有接口都长这样）

```json
{
  "code": 0,
  "message": "success",
  "data": {},
  "request_id": "a1b2c3d4e5f6",
  "timestamp": "2026-10-10T13:41:21+08:00"
}
```

| 字段 | 用途 |
| --- | --- |
| `code` | **唯一判断依据**。`0` 成功，非 0 是业务错误码 |
| `message` | 可直接展示给用户的提示 |
| `data` | 业务数据，无数据时为 `null` |
| `request_id` | **报障时把它贴给成员 1**，能直接定位日志 |
| `timestamp` | 服务器时间 |

### 1.3 错误码去哪里查

- **人看**：`docs/接口契约.md` 第三章，按分段列了全部错误码
- **代码用**：`app/core/errors.py` 的 `ErrorCode` 枚举

分段归属（新错误码必须申请自己区间的编号）：

| 区间 | 归属 |
| --- | --- |
| `1000~1099` | 通用 / 参数 / 权限 → 成员 1 |
| `1100~1199` | 账号、鉴权、个人中心 → 成员 1 |
| `1200~1299` | 第三方与生活工具 → **成员 2** |
| `1300~1399` | 打卡、积分、徽章 → **成员 2** |
| `1400~1499` | 待办、备忘录、记账、同步 → **成员 2** |
| `1500~1599` | 管理后台 → **成员 4** |

### 1.4 鉴权怎么用

登录/注册拿到 `access_token` 后：

```
Authorization: Bearer <access_token>
```

**Android 侧 Token 处理约定**（成员 3 重点看）：

| 收到 `code` | 含义 | 该做什么 |
| --- | --- | --- |
| `1003` | access 过期 | 静默调 `/auth/refresh` 换新 Token，**重放原请求**；刷新失败才跳登录 |
| `1004` | Token 无效 | 清本地登录态，跳登录 |
| `1108` / `1109` | refresh 失效 | 清登录态，跳登录 |
| `1005` | 无权限 | 提示「无权限」，**不要**跳登录 |

> **Token 时效**：access 2 小时，refresh 14 天。

### 2.3 三个必须遵守的实现约定

**① 第三方失败绝不能返回 500**

这是契约里特别强调的。天气接口的降级逻辑：

```python
# 有缓存 + 第三方失败 → code=0，标记 degraded
return ApiResponse.ok({
    ...cache_data,
    "from_cache": True,
    "degraded": True,     # 客户端据此提示"网络异常，展示缓存数据"
})

# 无缓存 + 第三方失败 → 才返回 1204
raise BusinessException(ErrorCode.WEATHER_NO_CACHE)
```

对应的错误码 `1202`/`1203` 是给**无需降级**的场景留的，正常降级走 `code=0`。

**② 打卡必须走事务，且不接受客户端传日期**

```python
# 连续天数、打卡日期都由服务端算，绝不信任客户端
today = datetime.now(ZoneInfo(settings.BUSINESS_TIMEZONE)).date()

# 以下 5 步必须在同一事务，任一步失败整体回滚
# 1. 查当天是否已打卡 → 2. 写 checkin_records → 3. 写 point_transactions
# 4. 更新 users.points_balance → 5. 判定并发放徽章
```

数据库有 `uq_checkin_user_date` 唯一约束兜底，并发也防得住。积分有 `uq_point_tx_source` 防重复发放。

**③ 同步接口要对 `client_id` 幂等**

同 `user_id + client_id` 重复上传，返回已有记录 + `code=0`，**不要报错、不要新建**。更新/删除必须校验 `version`，不一致返回 `1407`。

### 3.4 Token 刷新机制（重要）

后端用了**轮换策略**：

- 每次调 `/auth/refresh`，会同时给你**新的 access 和新的 refresh**
- **旧的 refresh 立即失效**，必须用新的替换本地存储
- 如果旧 refresh 被重复使用，后端会吊销你**所有设备**的 Token

所以 Android 侧要做的：

1. 用 `DataStore` 存 access + refresh
2. 刷新成功后**两个都覆盖更新**
3. 刷新请求加互斥锁，**避免并发刷新**（并发刷新会触发"旧 Token 复用"导致全部掉线）

> 这一条一定要做对，否则调试时会出现莫名其妙的"突然全部退出登录"。
